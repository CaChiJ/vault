# 1. 안정성과 성능의 스펙트럼
- 메시지 브로커에게는 빠른 성능이나 처리량 뿐만 아니라 **신뢰할 수 있는 메시지 전달(Guaranteed delivery)도 중요한 지표이다.** (e.g., 송금과 같이 미션 크리티컬한 서비스)
- 하지만 RabbitMQ에서 **메시지 전달 보장을 위한 여러 옵션들은 성능과 trade-off 관계에 있다.**

![[Pasted image 20260114110026.png|Performance will suffer when using each delivery guarantee mechanism, and even more so when they’re used in combination.|600]]
- 만약 하드웨어나 네트워크가 이상적으로 동작하기만 한다면 기본 구성만으로도 안정적이지만, 실제 환경에서는 예상치 못한 문제들이 발생한다. 미션 크리티컬한 애플리케이션이 아니라면 발생 가능한 모든 문제를 처리할 필요는 없다.
	- e.g., 각 서버의 메트릭을 쌓아두는 큐의 경우 → 일시적으로 소실되어도 큰 문제는 없다.

# 2. 메시지 보장 메커니즘
#### ◼️ `mandatory` 플래그
- `Basic.publish` RPC 명령을 보낼 때 `mandatory` 플래그를 설정하면,
	- 메시지 라우팅이 실패하는 경우에 발행자에게 메시지를 다시 보낸다. (`Basic.Return`)
	- 메시지 라우팅이 성공하는 경우에는 발행자에게 별도의 메시지를 보내지 않는다.
- 이때 "메시지 라우팅이 실패"한다는 의미는 발행된 메시지가 Exchange에는 도착했지만, 그 Exchange에 연결된 어떤 큐로도 메시지가 전달되지 못하는 상황을 의미한다.
- **이 옵션이 성능에 미치는 영향:** 반환 과정이 비동기로 동작하기 때문에 발행자가 대기할 필요가 없어 성능 저하가 미미하다.

#### ◼️ 발행자 확인 (`Publisher Confirm`)
- `Publisher Confirm`은 RabbitMQ의 확장 기능이다.
- `mandatory`는 라우팅 불가 상황(메시지를 넘길 바인딩이나 큐 존재 X)을 '실패'로 정의하는 반면, 발행자 확인은 애초에 Exchange가 존재하지 않거나 예기치 못한 내부 에러 등의 발생을 '실패'로 정의한다.
	- 다시 말해, 둘은 완전히 다른 실패 영역을 커버한다. (`mandatory`는 라우팅 설정 검증, `Publisher Confirm`은 브로커 처리 보장)
- `mandatory`는 라우팅이 실패한 경우에만 응답을 보냈다면, 발행자 확인은 성공 시 `Basic.Ack`, 실패 시 `Basic.Nack`를 응답한다.
- **이 옵션이 성능에 미치는 영향:** 비동기로 동작하면 가볍지만 발행자가 동기적으로 확인을 대기할 경우 지연이 발생해 성능이 떨어질 수 있다.

#### ◼️ 대체 익스체인지
- 익스체인지를 선언할 때 `alternate-exchange` 인수를 통해 라우팅 할 수 없는 메시지를 처리할 대체 익스체인지를 설정할 수 있다.
- **이 옵션이 성능에 미치는 영향:** 라우팅 실패 시 또 다른 곳으로 라우팅하는 단순한 내부 로직이므로 성능에 큰 영향을 주지 않는다.

#### ◼️ 트랜잭션으로 배치 처리하기 (TX)
- 메시지를 일괄로 MQ에 발행한 후, **큐에 커밋하거나 롤백**할 수 있는 원자적 메커니즘을 제공한다.
- **이 옵션이 성능에 미치는 영향:** 디스크 영구 저장(`persist`)과 결합할 경우 디스크 I/O를 그대로 대기하게 되어 엄청난 성능 저하를 유발한다.

#### ◼️ HA 큐를 이용한 장애 대응
- 클러스터 내의 어떤 노드에 큐의 복사본을 공유할지 지정할 수 있다. 기본 노드가 실패하면 보조 노드가 역할을 대신한다.
- 메시지가 전달되면 클러스터의 각 서버로 전송되고 한 노드에서 소비되면 다른 노드의 복사본도 즉시 제거된다.
- **이 옵션이 성능에 미치는 영향:** 클러스터 내 보조 노드들에 동기화하는 네트워크 비용이 발생하므로 응답이 지연된다.

#### ◼️ `delivery-mode 2` (디스크 저장)
- RabbitMQ는 기본적으로 메시지를 메모리에만 저장하며, `delivery-mode`를 2(`persist`)로 설정한 경우에만 메시지를 디스크에 저장한다. 큐도 반드시 `durable`하게 선언해야 한다.
- 이 경우 서버가 재시작된 후에도 여전히 메시지가 큐에 남아 있게 된다.
- **이 옵션이 성능에 미치는 영향:** 디스크 I/O를 수행하며 운영체제 커널이 차단되는 시간 동안 대기해야 하므로 성능 하락폭이 가장 크다.

# 3. RabbitMQ 푸시백 (TCP Back-Pressure)
- 과거에는 메시지 발행 속도가 너무 빠르면 `Channel.Flow` 명령을 보내 다시 명령을 보낼 때까지 메시지를 보내지 않도록 지시했다. 하지만 잘 무시되어 브로커가 터지는 일이 잦았다.
- 때문에 TCP Back-Pressure 메커니즘을 통해 아예 TCP 소켓 레벨에서 데이터 수신 자체를 중지하게 되었다.
- RabbitMQ는 내부적으로 연결마다 크레딧을 할당하고, 수신 시 크레딧을 차감, 완료 시 크레딧을 되돌려준다.
- 만약 속도가 미친듯이 빨라 크레딧이 0이 되면, 다시 크레딧이 생길 때까지 TCP 소켓 레벨에서 수신을 멈춘다. 블로킹으로 애플리케이션에 제동이 걸린다.

# 4. 적절한 아키텍처를 선택하는 데 필요한 질문
- 성능과 안정성 사이에 균형 지점을 찾아야만 한다. 이를 위해 다음과 같은 질문에 대답할 수 있어야 한다.

1. 발행자가 메시지를 디스크에 저장해야 하는가?
2. 애플리케이션의 다양한 구성 요소는 발행된 메시지가 수신됐는지 보장해야 하는가?
3. TCP Back-Pressure로 애플리케이션이 차단되거나, RabbitMQ에 메시지를 발행하는 동안 연결이 차단된 경우 어떻게 되는가?
4. 메시지가 얼마나 중요한가? - 메시지 처리량을 높이기 위해 Guaranteed Delivery를 희생할 수 있는가?
