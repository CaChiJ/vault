# 1. AMQP는 왜 필요한가?
- 단순 TCP 소켓만으로도 통신은 가능하지만, 실서비스에서는 "어디로 보낼지(라우팅)", "실패 시 어떻게 복구할지(전달 보장)", "상대 서비스 상태와 분리할지(비동기 디커플링)"를 매번 애플리케이션에서 직접 구현해야 한다.
- AMQP는 이 공통 문제를 프로토콜 레벨에서 표준화해, 서로 다른 언어/플랫폼 간에도 동일한 모델로 메시징을 구축할 수 있게 해준다.
- 즉, 애플리케이션은 비즈니스 로직에 집중하고, 메시지 전달/라우팅/흐름 제어는 브로커와 프로토콜에 위임할 수 있다는 점이 핵심이다.
- Enterprise 환경에서는 서로 다른 언어와 플랫폼(프레임워크)으로 작성된 독립적인 애플리케이션들을 관리한다.
- 이러한 애플리케이션들이 정보를 교환하며 함께 동작하게 해야 한다 → Messaging!
- Messaging은 Asynchronous하다.
- Asynchronous함으로써 얻는 이점은
	- Message를 받는 상대방이 `UP` & `READY` 일 필요가 없다.
	- 두 애플리케이션을 분리함으로써 응집력(Cohesion)을 높이고 결합도(Coupling)를 낮춘다.

# 2. AMQP as an RPC transport
- AMQP에는 요청/응답 형태로 동작하는 메서드가 있지만, RabbitMQ의 핵심 사용 패턴은 비동기 메시징이다.

#### ◼️ 대화 시작하기
1. 통신을 시작할 때, 클라이언트는 서버로 **프로토콜 헤더**를 전송한다.
	- 프로토콜 헤더는 명령이 아니며, 일반 AMQP 프레임과 별도의 초기 핸드셰이크 바이트 시퀀스다. 이는 서로가 알고 있는 언어(프로토콜)을 확인하는 과정이다.
2. 서버는 이에 대해 `Connection.Start` 명령으로 인사말에 응답한다.
3. 클라이언트는 다시 `Connection.StartOk` 응답을 보낸다.
![[Pasted image 20251229200428.png]]

#### ◼️ 올바른 채널로 튜닝하기 (Channel)
- AMQP 스펙은 Channel이라는 개념을 정의하고 있다.
- 하나의 Connection은 여러 개의 Channel을 가질 수 있다. Channel은 서로 다른 Channel 간의 데이터 전송을 격리한다.
- **TCP 연결 하나에 Channel을 다중화하는 이유가 뭘까?**
	- Connection은 TCP 연결을 의미한다. 각 스레드마다 하나씩 TCP Connection을 수립하는 건 비싸다.
	- 때문에 하나의 Connection에 여러 개의 Channel을 파두고, 스레드마다 하나씩 나눠주는 거다.
	- 1. 스레드 입장에서는 자신이 독자적인 TCP Connection을 가진 것처럼 다른 스레드를 고려하지 않고 작업할 수 있고
	- 2. 머신 입장에서는 TCP Connection 하나만 유지하면 되니 가볍다.

# 3. AMQP RPC 프레임 구조
- AMQP 스펙에는 객체 지향 개념과 유사한 형태로 명령이 정의되어 있다.
![[Pasted image 20251229201603.png|150]]

#### ◼️ AMQP 프레임 컴포넌트
- RabbitMQ에서 명령(Command)을 주고 받을 때 필요한 모든 인자들은 프레임이라고 불리우는 데이터 구조로 캡슐화된다.
- Frame은 명령과 인자를 구분하기 쉽게 해준다.
- 저수준의 AMQP 프레임은 다음과 같이 총 5가지 요소로 구성된다.
	1. 프레임 유형
	2. 채널 번호
	3. 프레임 크기
	4. 프레임 페이로드
	5. End-byte Marker
![[Pasted image 20251229202720.png|600]]
- 이 중 프레임 유형, 채널 번호, 프레임 크기를 프레임 헤더라고 부른다.

#### ◼️ 프레임 유형
- AMQP 스펙은 다음의 5가지 프레임 유형을 정의하고 있다.
	1. 프로토콜 헤더 프레임: RabbitMQ에 연결할 때 사용
	2. 메소드 프레임: RPC 요청이나 응답 전달에 사용
	3. 콘텐츠 헤더 프레임: 메시지의 크기와 속성을 포함
	4. 바디 프레임: 메시지의 내용을 포함
	5. 하트비트 프레임: 클라이언트와 서버가 주고 받으며 서로 사용 가능한 상태인지 확인

#### ◼️ 마샬링(Marshalling)
- 복잡한 데이터를 일정한 포맷으로 변환하는 과정을 마샬링이라고 한다.
- RabbitMQ에 메시지를 발행할 때, 데이터는 반드시 **메소드 프레임 → 헤더 프레임 → 바디 프레임** 순서대로 전송된다.
![[Pasted image 20251229205203.png|600]]

- **메소드 프레임**: 명령, 익스체인지와 라우팅 키를 포함.
![[Pasted image 20251229221045.png|600]]
- **콘텐츠 헤더 프레임**: 본문 크기, 메시지 속성을 포함.
![[Pasted image 20251229221115.png|600]]
- **바디 프레임**: 실제 메시지 내용을 포함.
	- AMQP에는 최대 바디 프레임이 있으며, 본문 크기가 이를 초과하면 바디 프레임을 여러 개로 분할한다.
![[Pasted image 20251229221135.png|600]]

# 4. 프로토콜: 컴포넌트 선언

#### ◼️ Exchange 선언
- Exchange를 선언할 때는 `Exchange.Declare`와 `Exchange.DeclareOk` 메서드를 사용한다.
- 만약 특정 이유로 `Exchange.Declare` 명령이 실패하면 `Channel.Close`에 실패 원인을 포함해 응답하고 채널을 닫는다.
![[Pasted image 20251229221237.png|450]]

#### ◼️ Queue 선언
- Queue를 선언할 때는 `Queue.Declare`와 `Queue.DeclareOk` 메서드를 사용한다.
- 동일한 `Queue.Declare` 명령을 두 번 이상 실행해도 문제가 되지 않는다. (Idempotent)
	- 이 경우 큐 내에 대기 중인 메시지 개수와 Consumer 수 등 큐 상태를 함께 반환한다.
- 만약 속성이 다른 동명이인 큐를 `Queue.Declare` 시도하면 채널을 닫는다.
![[Pasted image 20251229221434.png|450]]

#### ◼️ Bind하기
- `Queue.bind`를 통해 큐와 익스체인지를 연결할 수 있다.
![[Pasted image 20251229221657.png|450]]

# 5. 프로토콜: 메시지 발행 · 소비

#### ◼️ 발행하기
- 메시지를 발행(`Basic.Publish`)할 때는 `메소드 프레임`, `콘텐츠 헤더 프레임`, 그리고 하나 이상의 `바디 프레임`을 전송한다.
1. RabbitMQ는 메소드 프레임의 Exchange 이름을 이용해 데이터베이스에서 해당되는 Exchange를 가져오고
2. 찾은 Exchange에 연결된 binding들을 메서드 프레임의 라우팅 키와 함께 평가해, 적절한 큐를 찾는다.
3. 찾은 큐에 FIFO 순서로 메시지에 대한 참조를 삽입한다.
![[Pasted image 20251229221913.png|380]]
- 큐에는 메시지의 참조가 저장되므로, 여러 큐에 메시지가 들어가더라도 단 하나의 원본만 갖고 있기에 메모리를 낭비하지 않는다. 만약 데이터를 참조하는 큐가 더이상 없다면 원본 데이터는 메모리에서 제거된다.

#### ◼️ 소비하기
- Consumer는 `Basic.Consume`을 통해 큐를 구독한다.
- Consumer가 `Basic.Cancel` 명령을 보내기 전까지는 계속해서 활성 상태로 구독 상태를 유지해야 한다.
- RabbitMQ는 큐에 메시지가 들어올 때마다 `Basic.Deliver` 메소드 프레임과 컨텐츠 헤더 프레임, 바디 프레임을 전달한다.
- `no_ack`를 설정(true)하면 클라이언트가 `Basic.Ack`를 보내지 않아도 RabbitMQ는 계속해서 `Basic.Cancel` 명령을 수신할 때까지 `Basic.Deliver`한다.
- 반대로 `no_ack`가 비활성화되면 클라이언트는 `Basic.Ack` 프레임을 응답해야 하며, 어떤 메시지에 대한 `Basic.Ack` 응답인지 고유하게 구분할 수 있도록 `Basic.Deliver`에서 전달받은 배달 태그를 식별자로서 응답에 포함해야 한다.
