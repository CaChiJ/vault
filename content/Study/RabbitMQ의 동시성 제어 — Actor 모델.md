# 1. 배경
- Redis는 싱글 스레드 기반이므로 동시성 제어가 간단하다.
- 하지만 RabbitMQ는 멀티 스레드 기반이다. 그렇다면 동시에 서로 다른 스레드가 같은 큐로 메시지가 보내고자 할 때, 어떤 일이 일어날까?

# 2. Actor 모델
- 컴퓨터 공학에서 멀티 스레드 환경을 제어하는 두 가지 큰 패러다임은 (1)공유 메모리(Shared Memory)와 (2)메시지 패싱(Message Passing / Actor 모델)이 있다.
	- 공유 메모리는 프로세스 안에 공간을 미리 할당해두고, 여러 스레드가 락을 걸고 순차적으로 해당 공간을 이용하는 것이다.
	- 메시지 패싱은 각 스레드가 독립적인 메모리를 갖고, '메시지'를 주고 받으며 데이터를 교환하는 방식이다.
- RabbitMQ는 Erlang이라는 언어로 작성되었는데, 여기서 '프로세스'는 OS의 무거운 프로세스가 아니라 경량 스레드(Green Thread)다.
- 큐 하나당 전담 경량 프로세스(Actor)가 하나씩 붙는다.
	- TCP 연결로부터 요청을 받아, 프로토콜을 파싱하고, Exchange 라우팅 로직을 수행하는 건 네트워크 스레드가 담당한다.
	- 네트워크 스레드들은 요청 메시지가 들어갈 큐의 Mailbox에 메시지를 던지고 다시 떠난다.
	- 이때, Mailbox는 해당 스레드만 읽을 수 있고, 외부에서는 데이터를 넣을 수만 있는 공간이다.
- 큐에 붙은 Actor(프로세스)가 Mailbox에 쌓인 메시지를 순차적으로 처리한다.

# 3. 함정: persist 옵션의 한계
- 하지만 위 구조에는 치명적인 함정이 있다.
- 때문에, `persist` 옵션을 켰더라도, Mailbox에만 저장된 상태라면, Actor가 이를 아직 꺼내서 처리하지 않았으므로 디스크에 WAL 로그가 없다.
- 만약 이 찰나의 순간에 서버가 죽으면(`터진다`), 디스크에 기록되지 않았으므로 메시지가 영원히 유실된다.
- 즉, `persist` 옵션만 믿고 전송이 보장되었다고 착각하기 쉽지만 실제로는 그렇지 않다. 확실한 전송 보장을 원한다면 디스크 기록까지 마친 후 응답을 받는 Publisher Confirm(발행자 확인) 등 추가적인 메커니즘을 고려해야 한다.
