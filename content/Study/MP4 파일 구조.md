#### ◼️ Box
![[Pasted image 20260209230043.png]]
- MP4 파일의 모든 data는 'Box'(구 'Atom') 구조로 저장되어 있다.
- 각각의 box는 size, type(4 printable chars), version, data를 가진다.

| 필드        | 크기      | 역할                                                                                                            |
| --------- | ------- | ------------------------------------------------------------------------------------------------------------- |
| Size      | 4 bytes | 박스의 전체 크기(헤더 포함)를 나타내는 부호 없는 정수.<br><br>만약 값이 0인 경우에는 해당 박스가 파일의 끝까지 이어진다는 의미를 갖는다. (e.g., 파일의 마지막에 위치한 mdat) |
| Type      | 4 bytes | 박스의 종류를 나타내는 4글자의 ASCII 식별자(e.g., mdat, moov, ftyp)                                                           |
| LargeSize | 8 bytes | Size 필드 값이 1인 경우에만 존재한다. Size의 표현 범위(32비트)를 초과하는 박스의 크기를 명시한다.                                                |
| Data      | 가변      | 박스의 실제 Payload이다. 박스 안에는 필드 데이터 뿐만 아니라, 하위 박스들이 계층적으로 존재할 수 있다.                                               |

#### ◼️ MP4 File - Hierarchical View
- MP4 파일은 아래 그림과 같이 Box들의 계층적인 배치로 이루어진다.
![[Pasted image 20260209230434.png]]
- 가장 상위 레벨의 Box로는 ftyp, moov, mdat이 있다.
![[Pasted image 20260209230232.png]]
- moov와 mdat의 순서는 뒤바뀔 수 있다.
	- WebAPI Media Recorder로 녹화를 하고 나면 Seek(특정 재생 시점으로 이동)이 안되는데, 녹화 시점에는 파일 앞쪽부터 mdat을 쌓아가다가 녹화가 끝날 때 moov를 마지막에 삽입해주기 때문이다.
###### ftyp
- 다른 ISO file과의 호환성을 나타낸다.
###### moov
- 미디어의 모든 메타데이터를 저장한다. (메타데이터를 보고 싶으면 이 Box를 들여다보면 된다.)
###### mdat
- 실제 미디어 데이터를 저장한다.
- 이 박스는 내부에 **하위 박스 구조를 갖지 않는다. 단순히 연속된 바이너리**이다.
- 따라서 moov 박스 내부의 샘플 테이블(stbl)에 있는 오프셋 정보를 통해 이 박스 내에 원하는 정보의 위치를 특정해야 한다.

#### ◼️ Chunk와 Sample
- 일반적으로 `mdat` 박스 안에서 비디오 데이터와 오디오 데이터는 종류별로 뭉쳐 있지 않다.
- 각 Track(비디오/오디오)은 Chunk 단위로 interleaving 돼 있다.
###### Chunk
- Chunk 단위로 섞여 저장하는 이유는 다음과 같다.
	1. 동영상을 녹화할 때, 일정 주기로 메모리에 저장된 비디오/오디오 데이터를 파일로 내려 저장해야 한다. 각 Track 별로 뭉쳐 저장하려면 미리 충분한 공간을 예약해둬야 한다.
	   → 대부분의 경우, 앞으로 얼마나 더 녹화할지 미리 알 수 없다.
	2. 동영상을 재생할 때, 네트워크/디스크를 통해 데이터를 앞쪽부터 다운로드 받는다. 이때 Audio track이 전체 Video track 다음에 위치한다면, Video track 전체를 로드한 후 Audio track의 첫 N초를 로드하기 전까지 영상을 재생할 수 없다.
###### Sample
- 동영상의 각 track은 특정 시점의 단편적인 데이터(이미지)의 연속(배열)로 이루어 진다. (동영상 = 이미지1 + 이미지2 + 이미지3 + ...)
- 이때 각 track의 실제 데이터 형식(h264, vp8 등 코덱)에서 디코더가 처리할 수 있는 데이터의 최소 단위를 Sample이라 부른다.
	- 즉, MP4 영상을 재생할 때는 표시하고자 하는 시점의 sample을 해당 track의 디코더에 전달하면 된다.

- 정리하자면, **각 Track은 Sample들의 배열로 이뤄지며, 여러 Sample들을 Chunk로 묶어 (필요한 경우 Track 간에 Interleaving하여) 저장한다.**

#### ◼️ 원하는 샘플의 위치(mdat) 찾기

###### `moov.trak.mdia.minf.stbl` 메타데이터
- `moov.trak.mdia.minf.stbl` 에 위치한 메타데이터들을 이용해 논리적 시간 단위인 Sample을 물리적 바이트 위치인 오프셋으로 변환할 수 있다.
	- `stts(Time-to-Sample)`: 각 샘플의 재생 시간을 정의한다.
		- 더 정확하게는, `(sampleCount, sampleDelta)` 엔트리가 여러 개 놓인다.
		- 이 값의 의미는, 앞으로 나올 `sampleCount` 개의 샘플들은 모두 `sampleDelta` ms 만큼의 지속 시간을 갖는다는 뜻이다.
			→ 가변 프레임 레이트(VFR) 지원의 핵심
	- `stsc(Sample-to-Chunk)`: 여러 개의 샘플이 하나의 청크로 묶이는 방식을 정의
		- "몇  번 청크부터는 한 청크당 샘플이 몇 개씩 있다"는 압축된 형식으로 정보 제공
	- `stsz(Sample Size)`: 각 샘플의 개별 바이트 크기를 기록.
	- `stco/co64(Chunk Offset)`: 각 청크가 파일 시작점으로부터 몇 바이트 지점에 위치하는지 그 절대 주소를 기록한다.
	- `stss(Sync Sample)` : 랜덤 액세스가 가능한 키프레임(I-frame)의 샘플 번호 목록을 담고 있다.
###### 키 프레임의 샘플 오프셋 계산
1. 시간 범위 → 샘플 번호 범위(start, end)
	- `stts` 를 통해 원하는 시간 범위의 start 샘플 번호와 end 샘플 번호를 찾는다.
2. 샘플 번호 범위 → 범위 내 키 프레임
	- `stss` 을 통해 샘플 범위 내의 키 프레임 샘플 번호 리스트를 받는다.
3. 샘플 번호 → 청크 번호
	- `stsc` 테이블을 조회하여 샘플 $N$이 몇 번째 청크($C$)에 속해 있는지 파악한다.
4. 청크 번호 → 청크 오프셋 (바이트 단위의 절대 주소)
	- `stco` 테이블에서 청크 $C$의 시작 오프셋을 가져온다.
5. 청크 내 샘플 번호(순서) + 청크 오프셋 → 청크 내 샘플의 오프셋
	- 샘플 $N$이 청크 $C$의 첫 번째 샘플이 아니라면, 청크 내에서 앞선 샘플들의 크기를 모두 더해야 한다.
	- 이를 위해 `stsz` 테이블에서 청크 $C$에 속한 샘플들 중, 샘플 $N$ 보다 앞선 샘플들의 크기를 합산한다.

- 최종적으로는 파일 내에서 특정 샘플의 절대 주소(바이트 오프셋)을 다음과 같이 계산할 수 있다.
$$Offset_{Sample(N)} = Offset_{Chunk(C)} + \sum_{i=start\_of\_chunk}^{N-1} Size_{Sample(i)}$$
